✨ O QUE MUDOU?
═══════════════════════════════════════════════════════════════════════════

ANTES (Workflow Monolítico):
  ❌ Tudo rodava em 1 único job sequencial
  ❌ APK só começava DEPOIS do AAB terminar
  ❌ ~19 minutos de espera total
  ❌ Se um build falha, perde todo o progresso
  ❌ Difícil debugar onde falhou

AGORA (Workflow Paralelo):
  ✅ 7 jobs separados e organizados
  ✅ APK e AAB buildados SIMULTANEAMENTE ⚡
  ✅ ~14 minutos (economia de ~5 min!)
  ✅ Falhas isoladas não derrubam tudo
  ✅ Logs claros por job no GitHub UI

⚡ BENEFÍCIOS DA PARALELIZAÇÃO
═══════════════════════════════════════════════════════════════════════════

1. VELOCIDADE: ~30-40% mais rápido
   • APK e AAB buildados ao mesmo tempo
   • Não espera um terminar para começar outro
   • Runners GitHub isolados para cada job

2. RESILIÊNCIA: Falhas isoladas
   • Se APK falhar, AAB ainda completa
   • Se AAB falhar, APK ainda completa
   • Release pode ser criada mesmo com 1 build só

3. VISIBILIDADE: Logs organizados
   • Cada job tem log separado no GitHub UI
   • Fácil ver exatamente onde falhou
   • Status individual: ✅ ❌ 🟡

4. MANUTENIBILIDADE: Código limpo
   • Jobs pequenos e focados
   • Fácil adicionar novos builds
   • Fácil desabilitar o que não usa

5. FLEXIBILIDADE: Configurável
   • Pode rodar só APK, só AAB, ou ambos
   • Pode adicionar mais variants (debug, profile)
   • Pode adicionar builds de outras plataformas

🔧 COMO USAR O NOVO WORKFLOW
═══════════════════════════════════════════════════════════════════════════

OPÇÃO 1: Via GitHub UI (Recomendado)
────────────────────────────────────

1. Acesse: https://github.com/laylamonteiro/witchy-app/actions
2. Clique em "🚀 Build & Release Android"
3. Clique em "Run workflow"
4. Selecione:
   - Branch: main
   - Increment type: build/patch/minor/major
5. Clique em "Run workflow"
6. Aguarde ~14 minutos
7. ✅ Baixe APK e/ou AAB dos artifacts ou da release criada

OPÇÃO 2: Via Git Tag
─────────────────────

git tag v1.1.0
git push origin v1.1.0

→ Workflow roda automaticamente
→ Cria release com APK + AAB anexados

OPÇÃO 3: Script Local
──────────────────────

./scripts/bump_version.sh

→ Incrementa versão localmente
→ Opcionalmente faz build local
→ Opcionalmente commita e cria tag

❓ FAQ - PERGUNTAS FREQUENTES
═══════════════════════════════════════════════════════════════════════════

P: APK e AAB não têm dependência um do outro?
R: NÃO! São builds completamente independentes. Podem rodar em paralelo
   sem nenhum problema.

P: Por que não buildar tudo em um job só?
R: Paralelização! Dois runners buildando simultaneamente = 2x mais rápido.
   Além disso, falha isolada não derruba tudo.

P: E se eu não quiser gerar APK, só AAB?
R: Você pode desabilitar o job build-apk no arquivo .yml ou simplesmente
   ignorar o artifact APK gerado.

P: O cache funciona entre jobs paralelos?
R: Sim! Flutter e Gradle têm cache ativado. Cada job se beneficia do cache.

P: Posso adicionar mais builds? (ex: APK debug)
R: Sim! Copie o job build-apk, renomeie para build-apk-debug, e mude
   o comando para flutter build apk --debug. Vai rodar em paralelo também!

P: Quanto custa rodar isso?
R: ZERO para repositórios públicos. Para privados: 2000 minutos grátis/mês.
   Este workflow usa ~14 minutos = ~143 execuções grátis por mês.

P: Como vejo o progresso em tempo real?
R: GitHub Actions UI mostra status de cada job com cores:
   🟡 Amarelo = Rodando
   ✅ Verde = Sucesso
   ❌ Vermelho = Falhou
   ⚪ Cinza = Aguardando
